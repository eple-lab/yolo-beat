### D-01. 1차 추천 "책상 앞 코치" — 반려
- **내용:** 집중 타이머(person·cell phone 감지)와 거북목 알리미(Pose)를 묶은 서비스.
- **이유(추천했던 이유):** 사전학습 모델만으로 되고, 노트북 웹캠 위치(정면, 상반신)와 맞음.
- **결과:** eple이 요가 가이드 아이디어를 내서 넘어감.

### D-02. 요가 자세 가이드 — 반려
- **내용:** 요가 동작(난이도 1~10)을 보여 주고, 관절 각도를 비교해 교정 안내.
- **반려 이유:** 2D 웹캠의 깊이 한계, 전신 촬영 거리, 누운 자세 정확도, 음성 피드백 필요, 동작 정의 데이터 작업이 큼, 참고 이미지 저작권.
- **eple:** "그럼 별룬데. 간단하게 할 수 있으면서도 기발한 거 없을까?"

### D-03. 몸 악기 — 채택
- **대안:** 어깨 너머 감시자, 실루엣 통과 게임(Claude 추천), 집안 보물찾기, 허공 드로잉
- **이유:** eple이 고름("이거 좋아보여"). 손목 키포인트만 있으면 되고, 판정이 "점이 사각형 안에 있나"뿐이라 단순함.
- **예상했던 난관:** 지연(카메라 + 추론 + 오디오). 그래서 1단계에서 FPS부터 쟀다.

### D-04. 드럼 패드 6개 — 채택
- **대안:** 피아노 한 옥타브 8건반 / 드럼과 피아노 모드 전환
- **이유:** 패드가 커서 맞히기 쉽고, "때리는" 동작이 손목 움직임과 맞음. 피아노는 좁은 구역이 많아 오작동이 늘어남.

### D-05. 진입 순간 1번 — 채택 (보완 예정)
- **대안:** 진입 + 손목이 아래로 빠르게 움직일 때만
- **이유:** 단순함. 속도 조건은 튜닝할 게 늘어서 2차로 미룸.
- **실제로 생긴 문제:** eple: "친다기보다 손목이 영역에 들어가면 소리가 나오는 것 같아" → D-17

### D-06. numpy 합성 — 채택
- **대안:** 무료 샘플 wav 파일
- **이유:** 다운로드, 저작권 확인 불필요. 테스트로 길이·음량·감쇠를 검사할 수 있음.
- **결과:** eple이 들어 보고 "좋다".

### D-07. Python 데스크톱 앱 — 채택
- **대안:** B. Python 서버 + 웹 화면(FastAPI + WebSocket) / C. 브라우저만(ONNX Runtime Web)
- **이유:** 가장 빨리 동작을 확인할 수 있음. 웹은 구조가 두 배로 늘고, 브라우저 방식은 전·후처리를 직접 짜야 함.

### D-08. uv — 채택
- **대안:** conda 새 환경(Claude의 처음 제안), 기존 `myenv`, base에 직접 설치
- **이유:** eple: "콘다 말고 uv 있는데 이걸로는 안 돼?" 확인해 보니 uv 0.13.5와 uv가 관리하는 Python 3.14.7이 이미 있었음. 환경이 프로젝트 안 `.venv`에 생기고, `uv.lock`으로 버전이 고정됨.

### D-09. Python 3.14 — 채택
- **대안:** 3.12 (Claude가 처음에 호환이 불확실하다며 제안)
- **이유:** eple이 "검토부터 해줘"라고 함 → PyPI 조회 결과 필요한 패키지 전부 3.14 Windows wheel 있음([06](06-test-log.md) T-01). 짐작이 틀렸음.

### D-10. yolo11n-pose, 입력 크기 320 — 채택
- **근거:** CPU에서 640은 5~7 FPS, 320은 15~17.6 FPS(T-04, T-06). 손목 감지는 320에서도 90/90.
- **보류한 대안:** YOLO26n-pose(CPU에서 더 빠르다고 알려짐, 확인 안 함), OpenVINO 변환(Intel CPU 최적화). 기능이 먼저 돌아가야 지연이 실제로 거슬리는지 판단할 수 있어서 미룸.

### D-11. MSMF — 채택
- **근거:** DSHOW는 30fps를 요청해도 실제 15.3fps, MSMF는 30.0fps(T-05).
- **부작용(정정):** 처음에는 "`cap.release()`가 느리다"고 적었지만, 재 보니 MSMF와 DSHOW 모두 약 0.3초로 같았다(T-25). MSMF를 고른 데 따른 부작용은 확인된 것이 없다.

### D-12. 좌표와 배치 — 채택
- 정규화 좌표(0~1): 해상도와 무관.
- 가운데 열 비움: 얼굴·몸이 있는 곳.
- 왼쪽·위 경계 포함, 오른쪽·아래 제외: 붙은 패드 경계에서 두 번 울리지 않게.
- **알려진 문제:** 아래 패드(snare, kick)가 손을 쉬게 두는 위치와 겹침. 배치 조정은 소리를 붙이고 쳐 보면서 정하기로 함(남은 일).

### D-13. 쿨다운 120ms, 유예 3프레임 — 채택
- **이유:** 쿨다운은 경계 떨림 방지, 유예는 감지가 잠깐 끊겼을 때 재타격 방지. 14~17 FPS에서 3프레임은 약 0.2초.
- **실측:** 2회차에 같은 패드 150ms 이하 연타 0건(T-15).

### D-14. `src/` 구조 유지 — 채택
- **계기:** `uv init`이 계획에 없던 `src/yolo_detect/`와 `.git`을 만들었음.
- **이유:** 편집 가능 설치로 `python -m`이 어디서나 됨, 테스트 import가 깔끔함, 이름 변경이 쉬움.

### D-15. 테스트 먼저 + 뮤테이션 시험 — 채택
- **이유:** eple의 작업 방식(기대 결과를 먼저 적고, 일부러 실패하는 경우를 포함해 돌려 본 뒤 비교).
- **결과:** 8개 망가뜨림 중 7개 잡음, 1개는 등가 뮤턴트(T-10).

### D-16. 손끝 추정 방법 — 예정
- **계기:** eple: "손끝은 안 돼? 손목만 체크돼서." (손바닥은 crash 안에 있는데 손목 점은 hihat 경계에 있던 화면)

| 방법 | 시간 | 판단 |
|---|---|---|
| **A. 팔꿈치→손목 방향으로 아래팔 길이 × 약 0.7 연장** | 30분~1시간 | **선택.** 설치 없음. 손목을 꺾으면 어긋나지만 패드 치기에는 충분하다고 봄(추측) |
| B. 손 전용 21점 YOLO 모델 | 김 | Ultralytics에 데이터셋은 있지만 공식 학습 완료 모델은 없는 것으로 앎. CPU 학습 몇 시간 이상, 모델 2개라 FPS 절반 |
| C. MediaPipe Hands | 중간 | Python 3.14 지원 여부 미확인, YOLO 프로젝트 취지에서 벗어남 |

- **eple:** "오래 걸리는 거면 하지 말자" → B, C 안 함.

### D-17. 치는 동작 판정 — 예정
- **계기:** eple: "친다기보다 손목이 영역에 들어가면 소리가 나오는 거 같아. 친다는 액션을 확인하는 건 어렵겠지?"
- **방법:**
  1. **속도 기준:** 이전 프레임과 비교해 일정 속도 이상으로 들어올 때만 울림. 천천히 올려 둔 손은 안 울림 → T-15의 kick 연속 구간 같은 문제도 해결될 것으로 기대.
  2. **선분 통과 판정:** 14 FPS(약 70ms 간격)에서는 빠르게 치면 손이 패드 안에 있는 프레임이 하나도 없을 수 있다. "이전 위치 → 지금 위치" 선분이 패드를 지나면 타격으로 본다.
  3. **세기 음량:** 빠를수록 크게.
- **예상:** 테스트 포함 약 1시간 + eple이 쳐 보며 기준값 튜닝.

### D-22. AGPL-3.0-only — 채택

### D-23. 커밋과 저장소 — 채택
- **작성자:** git 설정을 바꾸지 않고 커밋마다 `eple-lab (Claude)`로 지정(eple의 작업 규칙). 사람이 직접 한 커밋과 구분된다.
- **메시지:** Conventional Commits, 한국어(`feat: …`, `docs: …`)
- **브랜치:** `master` → `main` (eple 요청)
- **저장소:** `eple-lab/yolo-beat`, 공개. 폴더는 eple이 `yolo-beat`로 복사한 뒤 옛 폴더를 지움.

### D-24. Ctrl+C 정리 중 에러 — 보류
- **현상:** 카메라를 닫는 약 0.3초 사이에 Ctrl+C가 한 번 더 들어오면 에러 메시지가 나오고 `total hits`가 안 찍힌다(T-16, T-25).
- **대안:** 정리 단계에서 Ctrl+C를 무시(`signal.SIG_IGN`).
- **이유:** 기능에는 영향이 없어 eple이 "고치지는 마"라고 함.

### D-25. 창 닫기(X) 버튼으로 종료 — 채택
- `waitKey` 다음에 `cv2.getWindowProperty(win, cv2.WND_PROP_VISIBLE) < 1`이면 루프를 나온다. `app.py`, `pose_preview.py` 두 곳(T-26).

### D-26. README 영상은 저장소에 넣기(B안) — 채택
- **대안 A:** GitHub 편집기에 끌어다 놓아 `user-attachments` 주소를 받기. README 안에서 재생이 확실하지만 eple이 직접 올려야 함.
- **B안:** `docs/videos/`에 mp4(8.5MB)를 넣고 README에 `<video>` 태그와 파일 링크를 함께 둔다. 8.5MB가 git 기록에 영구히 남는다.
- GitHub README가 저장소 안 mp4를 `<video>`로 재생하는지는 push 뒤 확인한다. 안 되면 링크로 GitHub 파일 화면에서 재생된다.
- 이미지 3장은 eple이 영상에서 캡처했다. 얼굴은 고양이 스티커로 가려져 있다.

### D-27. 타격감 작업 순서 — 손끝 먼저
- **eple 시험 소감:** 천천히 치면 소리가 안 나고, 작게 치면 더 안 났다. 손을 올리거나 내릴 때(진입 순간) 울리기도 한다.
- **순서:** ① 손목 점을 손끝으로 옮기기(D-16) → ② 지나간 길 판정(이전 점과 지금 점을 이은 선이 패드를 지나면 Hit, D-17) → 속도 판정(D-17)은 보류.
- **이유:** eple이 "손목이 잡히는 게 거슬린다. 손끝으로 옮기면 타격감도 맞추기 쉬울 것 같다"고 함. 판정 기준점이 손끝이어야 지나간 길 판정 기준도 맞출 수 있다.
