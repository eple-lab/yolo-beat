## T-01. Python 3.14용 wheel 확인

- **계기:** "Python 3.14는 PyTorch 호환이 불확실"이라고 했다가, eple이 "검토부터 먼저 해줘"라고 함.
- **기대:** (검토 전 짐작) torch나 torchvision에 3.14 wheel이 없을 수 있다.
- **방법:** ① `python -m pip index versions <패키지>` ② PyPI JSON API로 최신 버전의 wheel 파일 이름 조회
- **실제:**

  | 패키지 | 최신 | 3.14 Windows wheel |
  |---|---|---|
  | torch | 2.15.0 | `torch-2.15.0-cp314-cp314-win_amd64.whl` |
  | torchvision | 0.29.2 | `py3-none-win_amd64` (0.29.0, 0.29.1에는 `cp314` 전용도 있음) |
  | opencv-python | 5.0.0.93 | `cp37-abi3-win_amd64` |
  | pygame-ce | 2.5.8 | `cp314-cp314-win_amd64` |
  | numpy | 2.5.4 | cp314 |
  | scipy | 1.18.1 | cp314 |
  | matplotlib | 3.11.2 | cp314 |
  | pillow | 13.0.0 | cp314 |
  | pyyaml | 6.0.3 | cp314 |
  | psutil | 7.2.2 | abi3 |
  | polars | 2.1.0 | py3-none-any |
  | ultralytics | 8.4.208 | py3-none-any |

- **판정:** 짐작이 틀렸다. 전부 지원. 처음 torchvision 조회에서 cp314 줄이 비어 보였는데, 파일 이름이 `py3-none-win_amd64`(공용)라서 검색 패턴에 안 걸린 것이었다. 이전 버전 파일 목록을 따로 봐서 확인했다.

## T-04. FPS 벤치 (카메라 백엔드 DSHOW)

- **방법:** `uv run python -m yolo_beat.pose_preview --bench 60 --imgsz N` (워밍업 5프레임 후 60프레임)
- **기대(추측):** 640 → 8~12 FPS, 320 → 15~25 FPS

| imgsz | 카메라 읽기 | 추론 평균 | 추론 p90 | 전체 FPS | 손목 감지 |
|---|---|---|---|---|---|
| 640 | 0.3ms | 140.2ms | 191.3ms | 7.1 | 60/60 |
| 416 | 18.3ms | 48.4ms | 69.3ms | **15.0** | 60/60 |
| 320 | 27.9ms | 38.8ms | 61.8ms | **15.0** | 60/60 |

- **판정:** ⚠️ 416과 320이 정확히 15.0에서 같다. 추론이 빨라졌는데 FPS가 안 오르고 카메라 읽기 시간이 늘었다 → 카메라가 병목이라고 의심.

## T-08. 구역 판정 테스트 (TDD)

- **기대 동작(테스트 파일 docstring에 구현 전에 적음):**
  - `Zone.contains`: 안 True, 밖 False, 왼쪽·위 경계 포함, 오른쪽·아래 경계 제외
  - `default_drum_layout`: 6패드, 0~1 안, 겹침 없음, 가운데 비움
  - `HitDetector`: 진입 1번, 머묾 0번, 나갔다 다시 들어오면 1번, A→B 직행이면 B, 짧은 끊김(3프레임 이하)은 재타격 아님, 긴 끊김 뒤 재등장은 타격, 쿨다운 안 재진입은 막힘, 양손 같은 패드 같은 프레임이면 1번, 다른 패드면 2번
- **Red:** 구현 전 실행 → `ModuleNotFoundError: No module named 'yolo_detect.zones'` ✅ (실패가 기대)
- **Green:** 구현 후 `14 passed in 0.05s` ✅
- **앱 10초 실행:** 종료 코드 0, `total hits: 0`. 그동안 아무도 패드를 치지 않았다. 실제 타격 확인은 T-12.

## T-09. 소리·손 이름 테스트 (TDD)

- **기대 동작:**
  - `synth_all()`은 패드 이름 6개와 정확히 같다
  - 소리마다 float32 1차원, 길이 > 0.03초, 최대 진폭 0.3~1.0, 앞 10% 평균이 뒤 10% 평균의 5배 넘음(감쇠)
  - hihat이 가장 짧고 crash가 가장 길다
  - `to_int16(channels=2)`: int16, `(n, 2)`, C-연속, 두 채널 같음 / `channels=1`: `(n,)`
  - `hand_label(9) == "R"`, `hand_label(10) == "L"`
- **Red:** `ImportError: cannot import name 'hand_label'` ✅
- **Green:** `20 passed` (구역 14 + 소리 6) ✅

## T-10. 일부러 망가뜨린 코드 (뮤테이션 시험)

- **방법:** 소스를 스크래치패드에 복사 → `sed`로 한 줄 망가뜨림 → `PYTHONPATH`로 그 복사본을 먼저 불러오게 해서 테스트 실행. 원본은 건드리지 않음.
- **기대:** 망가뜨릴 때마다 테스트가 1개 이상 실패한다.

| 대상 | 망가뜨린 것 | 결과 | 판정 |
|---|---|---|---|
| zones | 오른쪽 경계도 포함 (`<` → `<=`) | 1 failed | ✅ |
| zones | 머무는 동안에도 울림 | 2 failed | ✅ |
| zones | 감지 끊김 유예 없음 | 1 failed | ✅ |
| zones | 쿨다운 없음 | 2 failed | ✅ |
| pose_preview | L/R 반전 안 함 | 1 failed | ✅ |
| sounds | 감쇠 없음 | 1 failed | ✅ |
| sounds | 최대 진폭 1.5 (클리핑) | 1 failed | ✅ |
| sounds | 스테레오 배열을 비연속으로 | 6 passed | ➖ 등가 뮤턴트 |

- **마지막 줄 설명:** 망가뜨린 코드가 `np.ascontiguousarray(...)` **안쪽**에 있어서 결국 연속 배열로 바뀌었다. 동작이 실제로 달라지지 않았으니 테스트가 통과하는 게 맞다. 테스트가 놓친 게 아니라 망가뜨리는 방식을 잘못 고른 것.

## T-11. 실제 오디오 장치 재생

- **발견 ①:** 화면 **오른쪽** 패드가 전부 `L` → 거울 반전 때문에 L/R이 반대. `hand_label()`로 수정(T-09).

- **발견 ④:** Ctrl+C로 끄자 긴 에러 메시지. → `KeyboardInterrupt` 처리 추가.
- **발견 ⑤:** eple: "난 소리를 못 들었어" → 이 단계에는 소리가 아직 없었다. 보고에서 이 점을 앞에 크게 쓰지 않은 것이 문제였다.

## T-15. 떨림 의심 구간 분석

- **기준:** 사람이 한 손으로 같은 패드를 일부러 칠 때 150ms보다 짧기는 어렵다고 보고, 그 이하 연타를 떨림 후보로 정했다.
- **결과:**
  - 같은 패드 간격 **150ms 이하: 0건** (쿨다운 120ms라서 120ms 미만은 원래 불가능)
  - **200ms 이하: 8건**

    | 간격 | 시각 | 패드 |
    |---|---|---|
    | 166ms | 40.93s | kick |
    | 169ms | 64.26s | snare |
    | 171ms | 60.76s | tom |
    | 172ms | 88.70s | crash |
    | 178ms | 81.08s | kick |
    | 181ms | 76.75s | hihat |
    | 192ms | 68.50s | tom |
    | 196ms | 26.49s | kick |

## T-25. `cap.release()` 시간 (MSMF vs DSHOW)

- **계기:** eple의 약 10분 실기 시험 로그도 `cap.release()` 줄에서 `KeyboardInterrupt` 에러로 끝났다(T-16과 같은 증상). "MSMF라서 닫기가 느리다"는 추측을 직접 확인했다.
- **방법:** 카메라를 열고 프레임을 몇 장 읽은 뒤 `cap.release()` 시간을 잼.

| 백엔드 | 기대(추측) | 실제 |
|---|---|---|
| MSMF | DSHOW보다 느림 | 310ms |
| DSHOW | MSMF보다 빠름 | 308ms |

- **판정:** ❌ 추측이 틀렸다. 두 방식 모두 약 0.3초다. 이 0.3초 사이에 Ctrl+C가 한 번 더 들어오면 T-16 에러가 난다.
- **두 번째 Ctrl+C는 어디서?(확인 못 함)**
  - 로그 끝의 `^C`는 두 번 누른 증거가 아니다. eple이 `pose_preview`를 Ctrl+C **한 번**으로 끝냈을 때도 에러 메시지 뒤에 `^C`가 찍혔다. 콘솔이 누른 키를 보여 주는 표시로 보인다.
  - 남은 가능성(추측): `uv run`이 Python을 자식 프로세스로 띄우기 때문에, 한 번 누른 Ctrl+C가 Python에 두 번 전달될 수 있다.
- **참고:** `pose_preview.py`에는 `KeyboardInterrupt` 처리가 없어서 Ctrl+C를 누르면 추론 도중 에러 메시지가 나오는 것이 정상이다.
- **에러 메시지 아래 `~~~^^^` 표시:** Python 3.11부터 생긴 기능으로, 그 줄에서 실행하던 표현식에 밑줄을 그어 준다. 에러가 따로 있다는 뜻이 아니다.

| 거리 | 기대 | 실제 (eple) |

| 가까이 | 가만히 있으면 안 울림 | ❌ 손목→손끝 연장 길이가 커서 떨림도 커지고, 떨림과 타격이 비슷하게 동작함 |
